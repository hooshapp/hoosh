# Physical iPhone — Anisha's execution guide

Read [shared readiness](README.md) and [iOS build/physical gates](../ios-shared-standalone.md) first. All cases begin **NOT RUN**. These stages supply IOS-C06 and VERIFY-C05 evidence; emulator/component passes do not close them.

**Important:** protection activation is currently compiled off. I00–I02 and available permission/picker checks can proceed on a correctly signed normal build. I03 contains a developer prerequisite; I04 enforcement must remain BLOCKED until it is resolved. This guide neither enables the gate nor supplies a diagnostic build that has not yet been prepared.

## I00 — Safe phone installation and reachable API (V19–20)

1. **I00.1 Spare phone:** use the agreed spare iPhone. Record model/iOS, existing app/version and required data. Current shared host bundle ID `com.AnishaDasgupta.DisconnectApp` matches the Swift pilot. Installing can replace it. Explicitly decide whether replacement on this phone is safe; do not uninstall, relink legacy identities or erase Keychain/App Group data to make room.
2. **I00.2 Signed candidate:** developer builds the normal Release app from the agreed source using the actual team/profiles. Inspect with `python3 scripts/inspect-ios-product.py <DEVICE_APP_PATH> --require-device --output <IGNORED_REPORT_PATH>`. Require the correct host, callback, native module and four expected extensions; actual matching App Group/Family Controls/Apple sign-in entitlements and nonexpired device provisioning. A simulator product is not installable-device evidence. Development capability is not distribution approval.
3. **I00.3 API:** a developer supplies an approved reachable HTTPS development API in the phone candidate. `127.0.0.1`/`localhost` means the iPhone itself; Android USB reverse does not solve this on iOS. Confirm expected project/schema and authenticated read/write, not just health. Do not disable TLS/trust validation or global transport security. Document separate Wi-Fi and mobile-data reachability if both are intended.
4. **I00.4 Install:** install/update the reviewed device artifact without data clear. Record source SHA, version/build, product/embedded-JS hash, signer check and activation-gate status from sanitized report. Stop on unexpected bundle/team/replacement/data-loss behavior.
5. **I00.5 Standalone:** with Metro stopped, launch by icon, background/reopen, terminate/reopen. Real Auth or correctly restored Home appears, not Swift enrollment, preview or a fixture account. On a genuinely fresh install test intro Skip and three distinct upward swipes with an animation each, then Continue → welcome → Sign up. One long swipe must not skip the three-count gate. Closing an unfinished intro should allow it again; explicit Skip/Sign up completes it and ordinary relaunch must not repeat it.

**Exit:** safe installed device product, signed native capability/configuration verified, reachable real API. Phone signing/configuration failure blocks subsequent native claims.

## I01 — Native Apple, Google, email links and session (V01–05)

1. **I01.1 Native Apple:** the test iPhone must be signed into its owner's Apple Account in iOS Settings; owner completes any password/2FA privately. Tap Continue with Apple in Hoosh. Expect native Apple sheet, deliberate consent and return to normal Home/expected Settings identity. Hide My Email relay is acceptable. Verify no prior Google identity/data appears unless the accounts are intentionally linked. Cancel another attempt; login stays usable and a fresh attempt succeeds. Do not treat Android Apple OAuth as this pass.
2. **I01.2 Google:** from login tap Continue with Google, accept the expected system browser handoff, observe chooser, choose approved test account and return. Dashboard and Settings match the chosen identity. Test success from signup, cancel/return and fresh retry. A stale browser tab is not a fresh request. No duplicated or unintended account should be created.
3. **I01.3 Fresh email:** using F, test empty/invalid fields and software keyboard. Enter valid credentials privately; expect confirmation guidance, no private flash. Record delivery and Inbox/Spam separately. Open newest confirmation on this same iPhone/request with Hoosh warm; repeat cold return using a separate disposable request/account. Correct authenticated route and identity must result. Do not add an age field to signup.
4. **I01.4 Password and logout:** wrong password gives a bounded error without private content. Correct password logs in. Logout hides all private tabs, swipe-back views and pending private toasts. Relaunch while signed out stays public.
5. **I01.5 Recovery:** request Forgot password for F, receive newest email, open on same iPhone with warm app, then separately cold app. Only correlated request enters reset form. Owner privately enters/submits new password. New password works on login, old fails. Cancel another request; direct reset-route access is refused. Coordinate disposable expired/reused links with developer; they must not authorize new changes or expose private data. Keep links off recordings/chat/Git.
6. **I01.6 Session/network:** background, terminate and relaunch signed in: same owner restores without duplicate action. Test no-internet login and interrupted provider return separately; honest retry/pending guidance, no false success. Restore connection and retry explicitly. Developer schedules real refresh/expiry and unavailable-storage/late-callback checks using sanitized diagnostics. Do not edit Keychain/session values. A controlled test and actual phone result stay separately labeled.
7. **I01.7 Recheck providers:** repeat one cancellation and fresh return after restarting Hoosh. Missing native entitlement, Apple Account setup prompt, delivery failure, provider rejection and app callback failure are distinct blockers. Capture message/timestamp without credentials and assign correctly.

**Exit:** native Apple and Google each accepted on this signed device; actual email/link/session subcases recorded. A native sheet opening alone is not sign-in success.

## I02 — Setup, profile and backend persistence (V06–08)

1. **I02.1 Screens:** with F follow current normal setup order, compare against Figma and test visible required inputs/selections, Back/Next and error placement. Record actual saved values using synthetic answers. 4. **I02.4 Profile:** save synthetic display name, reopen/relaunch; discard a different unsaved value; clear through explicit UI, verify blank and restore the original test value. No cross-account header flash.

Resolve through Check latest/Keep edits/review rather than silent overwrite. Developer separately interrupts API/reply-after-commit; one confirmed save, no duplicate replay or auto-Apply. If not reproducible on phone, record controlled-only evidence.
6. **I02.6 Existing warning:** inspect “Some settings couldn’t be loaded,” selected-app summary and native schedule readback on the correctly signed phone. Do not dismiss it as a simulator-only issue without evidence. Record failing capability/message; account save success does not prove native setup readiness.

**Exit:** actual owner-scoped persistence/resume works; native warning is resolved or explicitly blocks only affected stages. Saved draft is not installed protection.

## I03 — Permission, picker and timing feasibility prerequisite (V09–11)

1. **I03.1 Deny/allow:** from Hoosh's Screen Time setup choose Not now or deny authorization. Expect unavailable status and usable ordinary account pages. Request again only through explicit user action; owner grants when iOS permits. Return and refresh actual AuthorizationCenter status. No fake authorized flag, no silent Settings assumption.

Categories/domains are not equivalent to supported individual-app scope.
3. **I03.3 Interrupt:** background picker, return; cancel safely. Revoke authorization in Settings while editing, return and try Save. Expect truthful refusal and no falsely acknowledged new set. Regrant/recheck and explicitly retry. A stale picker/callback from A cannot save into B.
4. **I03.4 Check the gate:** record normal build capability/readback. If Apply is disabled because elapsed-expiry is unverified, mark dependent enforcement cases BLOCKED. Do not toggle a compiled flag, use a fake picker or equate successful schedule registration with successful expiry.
5. **I03.5 Developer timing candidate:** developer must prepare/review an isolated signed diagnostic timing candidate using the actual native extension path, identify bundle/data impact and obtain the phone owner's installation decision. Confirm whether a suitable harness currently exists; if absent, implementation remains prerequisite work. Do not run stale historical “no Apply UI” instructions as if they describe current code.
6. **I03.6 Timing proof:** on that explicitly reviewed candidate test shortest supported and longer temporary grants with T1 continuously foreground. Record request/start/deadline, native callback time, actual shield time/drift. Repeat reentry without deadline extension, switching T1/T2, lock/unlock, host termination and offline expiry. Test overlapping weekly/quest reasons and scoped Stop. Do not round up business deadlines to make SDK scheduling appear successful.
7. **I03.7 Decision:** developer compares actual timing/actions with approved shared semantics. Failure/impossibility requires an explicit scoped product/engineering decision, not silent substitution with pilot active-use limits. Only after accepted evidence and reviewed implementation may the normal activation gate change; build/inspect/install that new candidate and rerun I03/I04 on it. Diagnostic success alone is not final normal-app acceptance.

**Exit:** actual authorization/picker passes and a reviewed timing proof authorizes a specific normal candidate. Until then I04 and enforcement-dependent I05/I06 cases remain BLOCKED; auth/UI work can continue.

## I04 — Normal-app protection, allowances and quest overlap (V11–12)

Run only after I03 exits on a reviewed normal signed candidate.

1. **I04.1 Apply:** save active-window draft with T1/T2, two daily allowances and shortest supported duration. Review policy/zone/selection; nothing activates from Save. Explicitly Apply once. Require installed native readback/revision, then open T1 and observe a real shield/intervention. If response uncertain, Check readback; never blindly repeat writes.
2. **I04.2 Actions:** exercise supported Return home/temporary-access shield actions exactly as presented. Target must be left or temporarily allowed as intended. No notification/browser imitation counts as native shielding. An unavailable action stays a capability gap, not a pass because Android supports it.
3. **I04.3 Reentry/count:** start first allowance, record stopwatch/deadline/count. Leave/reenter T1 before expiry: original deadline and one consumed allowance. T2 has its own approved per-app budget. Do not import pilot minute-cap/extra-session rules. Exhaust allowances deliberately and record supported refusal/extra-access policy without undocumented bypass or budget reset.
4. **I04.4 Continuous foreground expiry:** leave T1 visible through elapsed deadline without opening Hoosh. Record actual shield and drift. If halfway nudge is advertised, verify it once and Keep going preserving deadline; otherwise record capability unavailability and whether this is an approved scope decision. Timer text or shield after reopening Hoosh is not foreground-expiry proof.
5. **I04.5 Account edit vs install:** edit account draft count/hours/minutes and Save. Existing native policy unchanged until explicit Apply. Apply a reviewed valid change during a consumed allowance; counts/deadline must follow approved preservation policy and not reset.
6. **I04.6 Overlap:** save two future synthetic quests overlapping each other inside the weekly window. Save does not Schedule. Explicitly Schedule and verify account/native acknowledgment. Observe all three reasons; Stop weekly only leaves both quests; Stop first quest leaves second; Stop last quest removes final reason. Record installed revisions and retained daily budget. If native UI cannot expose reasons, developer supplies sanitized native readback; no raw token/store dump.
7. **I04.7 Occurrences/edits:** test single-occurrence cancellation separately from recurring quest Stop. Review future edited occurrence; current occurrence snapshot remains immutable while future follows explicit update. Verify true window start/end and next recurrence when elapsed; do not infer execution from a label.

**Exit:** exact normal candidate demonstrates required native timing/actions, scope-preserving Stop and state readback independently of network/JS. A missing mandatory behavior keeps iPhone protection acceptance open.

## I05 — Rewards, recommendations and truthful History (V13–15)

1. **I05.1 Recommendation:** Accept an eligible suggestion once → one saved quest/cooldown, no automatic completion/credit/Apply. Reopen and retry; no duplicate. Test Skip separately when eligible. Use actual cooldown or another approved disposable account rather than editing storage.
2. **I05.2 Completion:** after a synthetic scheduled quest actually ends, explicit confirmation awards +50 once. Timer expiry alone does not award. Retry/read after relaunch and from second client, no duplicate. Before-end confirmation unavailable/rejected. Keep quest earnings and wallet balance distinct.
3. **I05.3 Feed:** sufficient balance and health below 100 → one explicit Feed costs 20, adds up to 20 capped at 100. Reopen/refresh retains result. Insufficient funds/full health no charge. Developer-assisted response loss recovers through Check last Feed without another spend.
4. **I05.4 Native receipt transport:** after supported native actions, developer verifies stable owner-scoped receipt upload/server acknowledgment and retry after network loss, no duplicate charge/award or wrong-owner ACK. iPhone allowance receipt transport does not establish confirmed-quit/day-coverage producers. Do not demand Android +5/+30/+20 awards where the iOS producer is explicitly unavailable; label unsupported with the capability decision, not fake success.
5. **I05.5 History:** open 7/28-day views/details, refresh. Current iPhone aggregate usage/saved-time measurement is unavailable. Expect explicit unavailable text; account turn-off receipts may be shown with source/coverage but Android account aggregates must not be labeled this iPhone's usage. No fabricated 0%/saved hours, baseline or streak dots. If a future iOS producer is implemented, it requires a new measurement/coverage acceptance run.
6. **I05.6 Cross-device account data:** compare same-account saved draft/wallet/quest status across the two real clients. Account values can sync; native selection/permissions/installed plans remain separate and no cross-device automatic activation occurs.

**Exit:** available account functionality and transport verified; unavailable producers remain honestly labeled and mandatory product gaps remain open.

## I06 — Native owner isolation and physical lifecycle (V16–20)

Enforcement-dependent cases require I03/I04 readiness. Account-only isolation can run earlier.

1. **I06.1 A→B:** with reviewed A rules active, record revision/count/deadline and distinct synthetic saved values. Logout A: private UI hides while installed rules remain. Sign into distinct B: no A profile, draft, setup, quests, wallet/History, app selection or delayed callback/toast. No auto-Apply/ACK of A data.
2. **I06.2 Claim Cancel:** choose Use this account on this device, cancel. A native rule/budget unchanged; B has not silently taken over.
3. **I06.3 Claim Confirm:** owner deliberately confirms. A rules stop before B can install; A private history/budget retained, B owns only its own state. Apply B's separate plan explicitly if needed. Return to A; own values/consumed counts restored without auto-resume, free allowance or B data.
4. **I06.4 Offline:** all network off during a real allowance with T1 foreground. Expiry/enforcement still occurs. Reconnect and read: no automatic Apply/replay, duplicates or native count reset. A local API outage alone is a different case.
5. **I06.5 Host termination:** start allowance then swipe Hoosh away; keep T1 foreground through deadline. Separately test background/foreground and lock/unlock. Native enforcement must not depend on an open RN screen, JS timer or API. Record actual event vs observed shield timing.
6. **I06.6 Reboot:** reboot spare phone within an installed window, unlock and test target/status. Record any before-first-unlock limitation; retained budgets/selection/history are not erased, expired sessions do not get fresh time. Ordinary app reopen is not a reboot pass.
7. **I06.7 Revoke:** revoke Screen Time authorization while configured, return/refresh; honest unavailable status, no false active claim. Regrant/review explicitly and verify real installed status before deliberate Apply. Save and permission must stay separate from activation.
8. **I06.8 Pending/late operations:** developer coordinates uncertain native install/ACK and delayed A response during logout/B login. Check readback/receipt before retry; stale generation cannot mutate B or ACK A journal. Do not corrupt real App Group files to simulate it; controlled diagnostics are distinct evidence.
9. **I06.9 Upgrade/legacy:** update from the actual previously used compatible candidate with data retained. Verify current owner, app selection, installed revision, counters/deadlines and pending receipts. A pilot replacement needs its own neutral legacy review and explicit Stop/reconfigure; no automatic participant-ID linking or telemetry import. Never ship an old reader against an incompatible newer native store to call rollback successful.

**Exit:** physical native behavior and isolation survived the named lifecycle transitions on this device, with no hidden store resets or auth bypass.
